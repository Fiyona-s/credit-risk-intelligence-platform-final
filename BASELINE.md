## B. Current architecture

### Traced inference flow (raw applicant → decision)

```
raw applicant dict/DataFrame (api.py body, or a Streamlit form/sample row)
        │
src.data.preprocessor.build_aggregate_features(df)
   left-joins cached one-row-per-SK_ID_CURR rollups of bureau, bureau_balance,
   previous_application, POS_CASH_balance, credit_card_balance,
   installments_payments (count/sum/mean/max aggregates, computed once per
   process and cached in a module-level global)
        │
src.data.preprocessor.engineer_features(df)
   adds CREDIT_INCOME_RATIO, ANNUITY_INCOME_RATIO, CREDIT_TERM,
   DAYS_EMPLOYED_RATIO, BUREAU_DEBT_CREDIT_RATIO; fixes the DAYS_EMPLOYED
   365243-sentinel anomaly -> NaN
        │
column alignment: any of the trained bundle's numeric_cols/categorical_cols
missing from df is added as null (tolerates a partial applicant record)
        │
pipeline.predict_proba() — a sklearn Pipeline of
  (1) ColumnTransformer: median-impute numeric, most-frequent-impute +
      OneHotEncoder(handle_unknown="ignore") categorical
  (2) LGBMClassifier (scale_pos_weight, monotone_constraints on
      AMT_INCOME_TOTAL/EXT_SOURCE_1/2/3)
        │
probability_of_default (float, 0-1)
        │
risk_band()  — src.utils.helpers, thresholds from .env
   (RISK_THRESHOLD_LOW=0.10, RISK_THRESHOLD_MEDIUM=0.30 by default)
        │
cost_optimal_decision()  — src.ml.predict, reads models/optimal_threshold.json
   "Decline" if probability >= optimal_threshold else "Approve"
   (separate, uncoordinated decision surface from risk_band — see § D)
        │
returned dict: probability_of_default, risk_band, cost_optimal_decision,
optimal_threshold, features_used
        │
   ┌────┴─────┬──────────────────┐
   ▼          ▼                  ▼
SHAP        surrogate rules   Streamlit / FastAPI response
(shap_      (rule_derivation,  (app.py's Risk Prediction tab shows all of the
explainer)   Business Rules    above plus the cost-sensitive threshold curve;
             tab)              api.py's /predict returns risk_score/risk_band/
                                top_shap_drivers only — NOT cost_optimal_decision,
                                NOT optimal_threshold — see § D)
```

### Training path

`src.ml.train.train()` calls the exact same `build_joined_dataset()` →
`engineer_features()` → `get_feature_columns()` sequence, then
`build_preprocessing_pipeline()` (same function `predict.py` loads the fitted
version of) is fit on the training split. The fitted `ColumnTransformer` +
`LGBMClassifier` are wrapped in an (already-fitted, never re-`.fit()`-ed)
`sklearn.Pipeline` and saved as one joblib bundle:
`{"pipeline", "numeric_cols", "categorical_cols"}`.

### Does training and inference use exactly the same feature-engineering path?

**Yes, confirmed by code inspection**, not merely assumed:
- Both call `src.data.preprocessor.build_aggregate_features()` — the same
  cached aggregate table.
- Both call `src.data.preprocessor.engineer_features()` — same ratio features,
  same anomaly fix.
- Inference re-derives `numeric_cols`/`categorical_cols` from the saved
  bundle (not by recomputing `get_feature_columns()` against the current
  input), so a differently-shaped inference-time frame is column-aligned to
  what the pipeline was actually fit on, rather than silently retraining the
  schema.
- Every one of `predict.py`, `shap_explainer.py`, `rule_derivation.py` follows
  this identical `build_aggregate_features → engineer_features → align
  columns` sequence before touching the pipeline. This is the single shared
  code path the module docstrings describe, and it holds up under inspection.

One inference-time subtlety: `build_aggregate_features()`'s module-level
`_aggregate_cache` is computed from whatever CSVs are present in the running
process (real Kaggle CSVs, if present) — a single applicant scored via the API
gets their *actual* bureau/previous-application history through this cache
keyed on `SK_ID_CURR`, not a synthetic/imputed default, provided the real CSVs
are mounted. In the deployed (no real CSV) case this cache is empty and
`build_aggregate_features()` is a no-op passthrough (confirmed in code: `if
_aggregate_cache.empty or "SK_ID_CURR" not in df.columns: return df`), so a
never-before-seen applicant with no local bureau data gets NaN for all
aggregate columns, imputed by the trained pipeline exactly like a training-time
applicant with no bureau history would be — consistent, not a special case.

### Feature engineering — current structure (pre-upgrade)

`src/data/preprocessor.py` already has five separate `_aggregate_*()`
functions (bureau, previous_application, pos_cash, credit_card,
installments) plus `engineer_features()` for ratio features — i.e. the
functional decomposition the upgrade prompt asks for largely already exists,
just under private (`_`-prefixed) names and without a feature
metadata/registry or an explicit "no history vs. zero value" distinction
beyond the two boolean flags below.

Existing distinction between "no history" and "zero value": `HAS_BUREAU_HISTORY`
and `HAS_PREV_APPLICATION` boolean flags are set from whether the row existed
in the raw aggregate merge (`.notna()` before fill), independent of the
filled numeric value — this already does what Milestone 1 asks for, for those
two tables only. POS/credit-card/installments have no equivalent
`HAS_POS_HISTORY`/`HAS_CC_HISTORY`/`HAS_INSTALLMENT_HISTORY` flag.

No feature metadata/registry file exists yet (source table, business meaning,
train/inference-eligibility, leakage classification) — confirmed absent.

No `src/data/feature_validation.py` or equivalent leakage-check module exists
yet — confirmed absent. The current leakage safety net is informal: code
comments in `preprocessor.py` assert (correctly, on inspection) that all
`DAYS_*`/`MONTHS_BALANCE` columns in every auxiliary table are `<= 0` relative
to the current application and therefore historical by construction, and
`get_feature_columns()` explicitly excludes `TARGET`/`SK_ID_CURR` from the
feature set — but there is no automated check that runs this reasoning and
reports pass/fail.

### Model development

Three models exist side by side, sharing one `_prepare_data()`/
`build_preprocessing_pipeline()` path and one 80/20 stratified split
(`random_state=42`):
- **LightGBM** (`train()`) — the only path that writes `models/credit_risk_model.joblib`.
- **Logistic Regression** (`train_baseline()`, `--baseline` flag) — reporting only, adds its own `StandardScaler`.
- **XGBoost** (`train_xgboost()`, `--xgboost` flag) — reporting only.

Also present: `cross_validate()` (5-fold CV, `--cv`), `tune()` (bounded
`RandomizedSearchCV`, `--tune`), SMOTE as an alternative to
`scale_pos_weight` (`--smote`).

**No probability calibration exists yet** — confirmed absent (no
`src/ml/calibration.py`, no `CalibratedClassifierCV` usage anywhere, no Brier
score computed anywhere in the codebase). `predict.py` returns the raw
LightGBM `predict_proba()` output directly as `probability_of_default` with
no calibration step.

**No structured `risk_score`/`model_version`/`feature_version` fields exist
yet** in `predict_applicant()`'s return dict — confirmed absent. The dict
currently returned is `{probability_of_default, risk_band,
cost_optimal_decision, optimal_threshold, features_used}`, not the richer
object the upgrade spec describes.

### Cost-sensitive decision optimization (already implemented)

`sweep_cost_sensitive_threshold()` in `train.py` runs after every default
training call, sweeping thresholds 0.10→0.90 (step 0.01) and computing
`total_cost = FP_COST × false_positives + FN_COST × false_negatives` on the
validation split, saving the full sweep (`thresholds`, `false_positives`,
`false_negatives`, `total_cost` arrays plus the argmin) to
`models/optimal_threshold.json`. `FP_COST`/`FN_COST` are `.env`-configurable
(default 1/5). The Streamlit Risk Prediction tab already has a
threshold-vs-cost chart and a live cost-ratio slider that recomputes the
optimum via pure arithmetic on the cached arrays (no retraining). **Not yet
present**: threshold-vs-recall / threshold-vs-approval-rate charts, named
scenario presets (Conservative/Balanced/Aggressive), and a
current-vs-cost-optimal side-by-side confusion-matrix comparison.

### Explainability (already implemented)

Per-applicant SHAP (`explain_applicant`, plain-language strings) and a
structured variant (`explain_applicant_structured`, used by `api.py`) both
exist, backed by one shared `_top_shap_contributions()` computation. A global
SHAP summary/beeswarm plot exists in the Explainability tab. **Not yet
present**: an explicit "Risk Drivers" vs. "Protective Factors" grouped
display (current output is a single ranked list, not split by direction), and
`src/explainability/counterfactual.py` does not exist.

### Rule derivation (already implemented)

`derive_rules()` fits a shallow surrogate `DecisionTreeClassifier` on the
model's own predictions (not ground truth) and converts `export_text` output
into IF/THEN sentences. **Not yet present**: per-rule coverage percentage,
per-rule model-agreement percentage, or per-rule risk prevalence — the current
output is rule text only, no supporting statistics.

### Fairness (already implemented)

`src/fairness/audit.py` computes, per `CODE_GENDER`/`NAME_EDUCATION_TYPE`
group: count, actual default rate, mean predicted risk score, predicted
high-risk rate, approval-rate proxy, true positive rate, disparity vs.
overall, and a >5pp flag; plus demographic parity difference and equal
opportunity difference at the attribute level. Small-group caution
(`MIN_RELIABLE_GROUP_SIZE = 30`) is implemented. **Not yet present**: any
mitigation experiment (proxy-feature removal, post-hoc per-group threshold
adjustment, or a fairness-aware training method) — confirmed absent, no
mitigation code exists anywhere in the repo yet.

### Monitoring (already implemented)

`src/monitoring/drift_report.py` covers **data drift** (per-feature, via
Evidently `DataDriftPreset`) and **target drift** (TARGET distribution) only,
comparing a saved `reports/reference_data.parquet` snapshot against a current
batch. **Not yet present**: data-quality checks (missingness/unexpected
categories/schema changes), prediction drift (distribution of predicted
probabilities/risk bands over time), or performance monitoring
(ROC-AUC/PR-AUC/Brier score over time when labels become available) —
confirmed absent in both `drift_report.py` and the Monitoring Streamlit tab.

### Chatbot (already implemented)

`src/talk_to_data/query_runner.py` enforces SELECT-only (via `sqlparse` token
scan), a fixed allowed table (`applicants`) and column allow-list, forbidden
DDL/DML keyword rejection, unknown-column-token rejection, and an auto-appended
`LIMIT`. `nl_to_sql.py` retries once on validation failure. Three-tier data
source: real local CSV → optional live Postgres (chatbot only, 8s hard
wall-clock timeout via `ThreadPoolExecutor`) → synthetic CSV fallback.

### API (already implemented)

`GET /health`, `POST /predict` only. `/predict` calls
`src.ml.predict.predict_applicant()` (same function the UI uses — single
inference path, confirmed no duplicated logic) plus
`explain_applicant_structured()` for top-3 SHAP drivers. **Gap confirmed**:
the API response omits `cost_optimal_decision`/`optimal_threshold`, which
`predict_applicant()` already computes and the Streamlit UI already shows —
so the UI and API are not fully at parity today despite sharing one inference
function. `POST /batch-predict`, `GET /model-info`, `GET /explain/{id}` do
not exist yet.

### Streamlit (already implemented)

8 tabs today: EDA, Risk Prediction, Model Evaluation, Explainability, Business
Rules, Fairness Audit, Monitoring, Chatbot. No landing/overview page — the
sidebar radio opens directly into whichever tab is selected, defaulting to
EDA. No Audit Trail tab, no Model Information tab, no Decision Optimization tab
distinct from Risk Prediction (the cost-threshold UI currently lives inside
the Risk Prediction tab itself).

### Decision audit trail — does not exist

Confirmed absent: no logging of individual predictions/decisions anywhere
(not in `predict.py`, not in `api.py`, not in `app.py`). No database table,
no append-only file, no audit schema. This is a net-new module for a later
milestone.

### Model versioning — does not exist

Confirmed absent: no `models/model_metadata.json`, no version string
anywhere in the codebase. The joblib bundle carries no version field; retrains
silently overwrite `models/credit_risk_model.joblib` in place with no history.

## C. Current baseline metrics (from README.md, previously measured — not re-derived in this audit; re-verify before quoting further if the model is retrained)

**Model comparison** (stratified 80/20 split, `random_state=42`):

| Model | PR-AUC | ROC-AUC |
|---|---|---|
| LightGBM (deployed, monotonic constraints) | 0.2760 | 0.7817 |
| XGBoost (`--xgboost`) | 0.2720 | 0.7791 |
| Logistic Regression (`--baseline`) | 0.2445 | 0.7648 |

**5-fold CV** (`--cv`): PR-AUC 0.2679 ± 0.0060, ROC-AUC 0.7790 ± 0.0039.

**Bureau/previous-app feature ablation + monotonic constraints**:

| Metric | Application-only | + Bureau/prev-app | + Monotonic (deployed) |
|---|---|---|---|
| PR-AUC | 0.2667 | 0.2761 | 0.2760 |
| ROC-AUC | 0.7735 | 0.7814 | 0.7817 |

**Confusion matrix @ 0.5** (deployed model): `[[41265, 15273], [1510, 3455]]`
(precision 0.1845, recall 0.6959, F1 0.2916).

**Cost-sensitive threshold** (`FP_COST=1`, `FN_COST=5`): optimal threshold
**0.67**, min total cost 19,954 (FP=5,684, FN=2,854 at that threshold) — this
number is generated fresh by `train.py` on every run and is **not
hardcoded**; it was independently re-confirmed live in Docker during this
audit's smoke test (model still loads, `models/optimal_threshold.json` still
present with `optimal_threshold: 0.67`).

**Fairness** (validation split): `CODE_GENDER` demographic parity difference
0.4603 (F 54.0% vs. M 69.8% predicted high-risk), equal opportunity
difference 0.0855; `NAME_EDUCATION_TYPE` demographic parity difference
0.2905, equal opportunity difference 0.1954 (42.5%–71.6% range across
education groups). Both **substantially exceed** the 5pp flag threshold —
unmitigated, as designed.

**Hyperparameter tuning** (`--tune`, 15-iter `RandomizedSearchCV`): found only
+0.0020 ROC-AUC over defaults — smaller than 5-fold CV noise (±0.0039);
defaults kept.

All of the above are figures already measured and documented in `README.md`
prior to this audit; this document does not re-run training (out of scope for
Milestone 0, and re-running would cost ~2 minutes per pass with no benefit
since nothing changed). The live Docker smoke test in § "Application status"
below confirms the *currently saved* model still loads and scores correctly,
which is the relevant baseline check for this milestone.

## Current known limitations (as already documented in README.md, restated here for completeness)

- Surrogate-tree rules approximate the model's boundary; can disagree with
  LightGBM at rule boundaries. No coverage/agreement statistics reported per
  rule (gap, noted above).
- Real, substantial fairness disparities exist by gender and education,
  unmitigated.
- SQL validator is a token-scan safeguard, not a full parser.
- Monitoring drift ranking mixes p-value and distance-based methods
  (correctly handled per-column, but cross-method severity ordering is
  approximate).
- Bureau/previous-app features are simple per-applicant rollups; no
  recency-weighting or trend features.
- Validated only on a random 80/20 split; no time-based validation yet
  despite credit data's temporal structure.
- Monotonic constraints cover only 4 of ~291 trained features.
- Cost-optimal threshold (0.67) and the fixed risk-band threshold
  (`RISK_THRESHOLD_MEDIUM=0.30`) are two independent, uncoordinated decision
  surfaces — both exposed in the UI, neither reconciled with the other.

## D. Problems discovered

1. **No test suite or CI at all.** Every "verification" to date has been
   manual (Docker rebuild + curl/CLI smoke tests). This is the single
   biggest technical risk for a project of this size going forward — a
   regression in `preprocessor.py` or `predict.py` would currently only be
   caught by chance, not by design.

2. **API/UI parity gap.** `predict_applicant()` already computes
   `cost_optimal_decision` and `optimal_threshold`, and the Streamlit Risk
   Prediction tab already displays them — but `api.py`'s `/predict` response
   model (`PredictResponse`) does not expose either field. Anyone integrating
   against the API today gets a materially incomplete decision compared to
   the UI, despite both nominally sharing "one inference path."

3. **The trained model artifact (`models/credit_risk_model.joblib`, 1.1 MB)
   is committed to git**, while `models/optimal_threshold.json` (generated by
   the same training run) is not. This is an inconsistent policy — either
   both training-run artifacts should be versioned the same way, or neither
   should be, and a real model-versioning scheme (Milestone 12) needs to
   decide which.

4. **No feature metadata/registry and no automated leakage validation.** The
   leakage reasoning that exists (DAYS_*/MONTHS_BALANCE columns are all ≤ 0,
   TARGET/SK_ID_CURR excluded from features) is currently only informal code
   comments — correct on inspection, but not machine-checked, so a future
   change to the aggregation logic could silently introduce leakage with
   nothing to catch it.

5. **No probability calibration.** The raw LightGBM `predict_proba()` output
   is used directly as `probability_of_default` everywhere (risk banding,
   cost-threshold sweep, SHAP, the model card). `scale_pos_weight` is known
   to distort the *scale* of predicted probabilities (this is explicitly
   already documented in README.md as the explanation for why the
   cost-optimal threshold is 0.67, well above naive intuition) — meaning
   probabilities today are good for *ranking* but have not been verified to
   be good for *reliability* (e.g. "of applicants scored at 40%, do ~40%
   actually default?"). This is exactly the gap Milestone 4 (calibration)
   is meant to close, and the existing 0.67-threshold finding is itself
   indirect evidence calibration is needed.

6. **No decision audit trail.** Every prediction is stateless and ephemeral
   today; nothing is persisted per-decision (not even in Streamlit's
   `session_state`, which only holds the *last* prediction for
   cross-tab reference, not a history). A "why did the system decide X at
   time T" question cannot currently be answered after the fact.

7. **Monitoring has real gaps against the stated production-monitoring
   story.** Data drift and target drift are implemented; data quality,
   prediction drift, and performance monitoring are not. The Monitoring tab
   currently cannot answer "is the model's own output distribution
   shifting" or "is missingness increasing" — only "have raw feature/target
   distributions shifted."

8. **Two leftover shell scripts (`fix_repo.sh`, `fix_repo2.sh`) and a `.venv/`
   directory sit in the repo root**, unrelated to the application itself
   (from earlier git-history cleanup work). Not urgent, but should be
   deleted or gitignored before a portfolio-facing cleanup pass, so a
   reviewer opening the repo doesn't find unexplained scripts.

9. **Rule derivation has no fidelity statistics.** `derive_rules()` produces
   IF/THEN text but nothing quantifying how well the surrogate tree actually
   agrees with the underlying LightGBM model, nor how many applicants any
   given rule covers — both explicitly requested by the upgrade spec and
   currently unmeasurable without new code.

10. **No fairness mitigation exists**, only measurement. This is by design
    so far (the project correctly avoids quietly tuning thresholds to look
    fairer), but it means Module 10's "fairness-performance trade-off table"
    genuinely starts from zero — no mitigation code, no comparison numbers,
    nothing to reuse.

None of the above are regressions or breakage — the currently deployed system
works, as confirmed by the live smoke test. They are gaps relative to the
target architecture, which is exactly what Milestone 0 is meant to surface.

## E. Recommended implementation order

The priority order in the original upgrade prompt (Phase 1 → 6) already
matches what this audit found to be the actual dependency chain, with one
adjustment: feature metadata/leakage validation should land immediately after
(not deeply inside) the feature-engineering refactor, since calibration,
risk-scoring, and later the audit trail all want a stable, validated feature
contract to build on. Concretely:

1. **Feature engineering refactor** (rename/expose the existing `_aggregate_*`
   functions, add the domain features listed in the spec that aren't already
   present, add the missing `HAS_*_HISTORY` flags for POS/credit-card/
   installments, add the feature metadata registry) — builds directly on
   code that already exists and is already well-factored; lowest risk, do
   first.
2. **Feature leakage validation** — write once the feature registry exists,
   so it can check against declared metadata rather than re-deriving rules
   from scratch.
3. **Model comparison cleanup + calibration** — calibration is the first
   genuinely new modeling capability; it changes what "probability of
   default" means downstream, so it must land before risk scoring is
   restructured around it.
4. **Risk scoring engine upgrade (`predict.py`)** — now has calibration,
   validated features, and model versioning (should be pulled slightly
   earlier than Module 12's original position, or at least stubbed then, since
   the structured prediction object the spec wants includes `model_version`/
   `feature_version`).
5. **Cost-sensitive decision optimization upgrade** — already has a solid
   foundation (§ B); extend in place.
6. **SHAP decision explanation + counterfactual** — counterfactual explicitly
   depends on knowing which features are "actionable" (income, credit amount,
   external score, employment duration), which the feature metadata registry
   from step 1 should supply directly (an `inference_allowed`/`actionable`
   flag), so counterfactual work benefits from doing step 1 first.
7. **Model-to-policy rules upgrade** (coverage/agreement stats) — independent,
   can happen any time after step 4.
8. **Fairness mitigation experiments + trade-off table** — independent of the
   above; can run in parallel once calibration is done (since PR-AUC/recall
   comparisons should be on calibrated probabilities for consistency).
9. **Model versioning + decision audit trail + API/monitoring upgrades** —
   productionization phase, depends on steps 3-4 (needs `model_version`/
   `feature_version`/calibration fields to exist before it can log them).
10. **Testing + CI** — should really be interleaved with every step above
    (add a test alongside each new module, not deferred to the end), given
    finding #1 above; treat "add or expand tests" as a per-milestone
    requirement, not a separate final phase.
11. **Streamlit redesign, README rewrite, model card update** — last, once
    the underlying modules it needs to describe/display actually exist.

This document establishes the baseline. No code was modified. Ready for
Milestone 1 on your instruction.
