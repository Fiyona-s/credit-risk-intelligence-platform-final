# Major Design Decisions

A brief note on the key choices behind this platform and why they were made. Full detail and supporting numbers for each of these live in `README.md`; this file is the condensed version.

## Modeling

- **LightGBM over logistic regression.** Chosen for native missing-value handling and strong tabular performance without heavy tuning. This claim is backed by an actual baseline (`python -m src.ml.train --baseline`): LightGBM beats a properly-scaled logistic regression on PR-AUC (0.276 vs 0.245) more clearly than on ROC-AUC alone (0.782 vs 0.765) — the gap is real but smaller than a confident "chosen over logistic regression" line might suggest. Reported honestly rather than only citing the flattering metric.
- **`scale_pos_weight` over SMOTE for the ~92/8 class imbalance.** At this scale and dimensionality, SMOTE's synthetic minority samples tend to land in unrealistic regions of the one-hot feature space and mainly add training cost without improving ROC-AUC/PR-AUC over a correctly weighted loss. SMOTE remains available (`--smote`) for comparison, not removed.
- **PR-AUC as the primary metric, not ROC-AUC.** With ~92/8 imbalance, ROC-AUC can look deceptively strong while still performing poorly on the minority default class that a screening tool actually cares about. Both numbers are reported; PR-AUC leads.
- **Cross-validation and hyperparameter tuning are opt-in, not default.** A single 80/20 split has no confidence interval on its own, so `--cv` (5-fold) exists for honest stability reporting, and `--tune` (bounded `RandomizedSearchCV`) exists to check whether the hardcoded defaults are leaving real performance on the table. Neither is part of the default `python -m src.ml.train` run, which stays fast (~50s) for a first clone. Tuning found only a +0.002 ROC-AUC gain — smaller than the CV's own ±0.004 fold-to-fold noise — so the defaults were kept rather than chasing noise.
- **Monotonic constraints on 4 features only, not blanket.** `AMT_INCOME_TOTAL` and `EXT_SOURCE_1/2/3` get a `monotone_constraints=-1` (higher value can never increase predicted risk) — the kind of constraint a fair-lending review can reasonably expect for these specific features. Deliberately *not* applied to features like `CNT_CHILDREN` or `DAYS_EMPLOYED`, where the real-world risk relationship is plausibly non-monotonic and forcing a direction would be dishonest, not more rigorous. Measured cost here: effectively zero (checked, not assumed).
- **Bureau/previous-application features are empirically justified, not assumed.** Before joining six auxiliary Home Credit tables into the pipeline, a dedicated EDA finding (insight #6) measured a real 2.4-point default-rate gap between applicants with and without bureau history in the raw data. The join followed from that measurement, not from generic domain knowledge about credit datasets. The same `build_aggregate_features()` function is called by training, inference, and explainability code, so features can't silently drift between train and serve time.
- **Surrogate decision tree for business rules, not the model itself.** A shallow tree trained to mimic the LightGBM model's own predictions gives a credit-policy analyst readable if/then rules, at the cost of occasionally disagreeing with the underlying model near split boundaries — documented as an explanatory aid, not a replacement scoring engine.

## Data & infrastructure

- **DuckDB instead of a full database server for talk-to-data.** Embedded, zero infrastructure, queries CSVs/Parquet/Postgres directly — fits the free-tier-only constraint without standing up a separate DB service for local use.
- **Three-tier chatbot data source, in priority order: real local CSV → optional live Postgres → committed synthetic fallback.** The real Kaggle dataset is correctly never committed to git, so a deployed instance would otherwise always show empty/broken chatbot behavior. DuckDB can instead attach a Postgres database live (loaded once, out of band, via `scripts/load_dataset_to_postgres.py`) so a deployed app can serve real data without the dataset ever touching git or the Docker image. Any failure at the Postgres step (unset/wrong URL, unreachable host, missing table) is caught and logged, falling through cleanly to the synthetic dataset rather than crashing — verified with real failure-mode tests, not just happy-path.
- **A synthetic fallback dataset is committed; the real dataset never is.** `data/sample_applicants.csv` is generated (`scripts/generate_synthetic_data.py`, fixed seed) with distributions calibrated to match this project's own documented real-data findings (8% base default rate, the bureau-history default-rate gap) — directionally honest for demos, never a substitute for evaluating real model quality.
- **Groq free tier as the primary LLM, Gemini free tier as automatic fallback.** Both are genuinely free-tier, no credit card — Groq is used first for latency; either failing falls through to the other, then to a graceful "couldn't answer" message rather than a crash.
- **A small set of few-shot examples in the SQL-generation prompt.** ~190 tokens added to every chatbot call, traded for measurably more consistent SQL on ambiguous phrasing ("risky applicants," "compare genders") — a deliberate, documented cost, not a free upgrade.
- **A token-scan SQL safety layer (`sqlparse`-based allowlist), not a full SQL parser.** Rejects non-`SELECT` statements, unknown tables/columns, and enforces a row limit — covers the required query patterns robustly; documented as not a formal guarantee against every conceivable malformed statement.
- **One Docker image for both local and deployed use.** The same image runs via `docker-compose up` locally or as a Render web service — `POSTGRES_URL` is the only environment-specific configuration difference between the two.
